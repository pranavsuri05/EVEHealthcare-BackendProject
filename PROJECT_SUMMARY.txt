DATABASE SCHEMA
================================================================================

7 Tables (Normalized to 3NF):

1. users
   - id (PK), email (UNIQUE, INDEX), hashed_password, timestamps

2. diagnostic_centres
   - id (PK), name, location, timestamps

3. diagnostic_tests
   - id (PK), name (UNIQUE, INDEX), description, timestamps

4. centre_tests (KEY JUNCTION TABLE)
   - id (PK), centre_id (FK), test_id (FK), price, available
   - UNIQUE(centre_id, test_id) - prevents duplicates
   - Enables same test at different prices at different centres

5. bookings
   - id (PK), user_id (FK), centre_test_id (FK), centre_id, test_id
   - appointment_date, amount (price snapshot), status, timestamps
   - INDEXes on user_id, centre_id, test_id, status

6. payments
   - id (PK), booking_id (FK), amount, status
   - provider_event_id (UNIQUE) - ensures webhook idempotency
   - INDEXes on booking_id, status, provider_event_id

Key Design Points:
✅ Price snapshot in booking table (immutable at booking time)
✅ Unique constraint on provider_event_id for webhook safety
✅ Foreign keys enforce referential integrity
✅ Indexes on frequently queried columns for performance

================================================================================
DESIGN HIGHLIGHTS
================================================================================

1. JUNCTION TABLE (centre_tests)
   Problem: Same test at different centres with different prices
   Solution: Separate centre_tests table with centre_id + test_id + price
   Benefit: Flexibility, normalization, clean separation

2. PRICE SNAPSHOT
   Problem: Booking should remain same price even if centre changes it later
   Solution: Capture price in booking.amount at creation time
   Benefit: Prevents disputes, clear audit trail, immutability

3. WEBHOOK IDEMPOTENCY
   Problem: Network retries can deliver webhooks multiple times
   Solution: UNIQUE constraint on provider_event_id at database level
   Benefit: Foolproof (no app-level race conditions), atomic, scalable

4. DETERMINISTIC PAYMENT TESTING
   Problem: Tests need reliable payment outcomes (not random)
   Solution: MockPaymentProvider accepts explicit success/failure flag
   Benefit: Tests are deterministic, repeatable, trustworthy

5. CENTRALIZED EXCEPTIONS
   Problem: Inconsistent error responses across endpoints
   Solution: Centralized HTTPException subclasses (401, 403, 404, 409, 422)
   Benefit: Consistent API errors, easy to maintain, clear HTTP semantics

6. SERVICE LAYER
   Problem: Business logic mixed with route handlers
   Solution: Separate services (auth_service, booking_service, payment_service)
   Benefit: Reusable logic, easier testing, clear responsibilities
